# 秒杀系统设计 · 面试口述稿

> 用法：这份稿子按"设计者自述"写，不引用代码行号。每题先给结论，再给设计，再给取舍。
> 面试时的原则：**先说结构，再说细节，最后说边界**。边界不是缺点，是设计成熟度。

---

## 0. 开场：一句话讲清整体设计

如果面试官说"你先讲讲你的秒杀是怎么设计的"，用这一段开头，后面所有问题都能挂上去。

> 我把整个系统拆成**三层漏斗 + 一条事实链 + 一个收敛机制**。
>
> **三层漏斗**解决"流量"：第一层限流（本地令牌桶 + Redis 三级配额），第二层资格校验（活动白名单/预约），第三层 Redis Lua 原子预占。每往下一层，流量少一个数量级，最终打到数据库的请求被压缩到库存量级。
>
> **一条事实链**解决"一致性"：我用 `reservation_id` 作为贯穿全链路的业务主键。它在网关生成，写进 Redis 的预占 Hash、Redis Stream 的消息、Kafka 的事件、MySQL 的订单表和幂等表。所有幂等、补偿、对账都挂在这一个 ID 上。
>
> **一个收敛机制**解决"偏差"：预占和落账不可能在同一个事务里，所以失败就立即幂等回补，补偿失败就重投，重投还不行就对账兜底。
>
> 一句话概括设计哲学：**Redis 负责"挡人"，MySQL 负责"定案"，中间用幂等和补偿收敛，不追求跨系统的 Exactly Once。**

这个开场之后，面试官问的每一个问题，你都可以先说"这属于漏斗的哪一层"或"这是事实链上的哪个环节"，答案自然成体系。

## Q36 Redis 扣减库存、消息进 MQ 后，MySQL 实际扣减失败怎么办

**结论：按失败性质分两类处理——业务性失败立即补偿，基础设施失败交给重投，全部靠 reservation_id 做幂等。**

先说清为什么会失败。MySQL 侧扣减失败只有两种性质：

**第一类，业务性失败。** 说明 Redis 放行多了。具体三种：
- 订单唯一键冲突，同一个人重复下单；
- 活动库存条件更新影响行数为 0，MySQL 侧真的没货了；
- 持久库存可用量更新失败。

这类失败是"确定性的、重试也没用"的，必须**立即回补 Redis**，否则这个名额在整个活动期间都是死名额，直接变成少卖。

回补的设计要点是**幂等**：我以 `reservation_id` 为幂等键，在预占记录上做状态机，只有 `reserved → released` 这一次状态转换才会执行库存加回。重复调用第二次会发现已经是 `released`，直接返回"已处理"，不会多加。这样无论消息重投多少次，库存只会还一次。

**第二类，基础设施失败。** DB 超时、连接断、死锁。这类失败**不能吞**，也不该盲目补偿——因为事务可能已经提交但响应丢了，补偿会造成超卖。我的做法是直接返回错误、**不提交 offset**，让消息重投，重投后靠两个幂等点收敛：`processed_events` 表判断事件是否处理过，预占记录的状态机判断库存是否已还。

**补偿的顺序我也刻意设计过**：先补 Redis，再写"已拒绝"的事实。这两个动作不在一个事务里，所以存在一个窗口——Redis 已经还了库存，但 MySQL 还没记录。如果这时候进程挂了，重投后会再走一次补偿，发现状态是 `released`，跳过，然后继续写记录，最终收敛。顺序反过来就危险了：先记"已处理"再补库存，一旦中间崩溃，这条预占就永远没人还，是真正的永久少卖。**原则是宁可多跑一次空补偿，也绝不能漏补。**

**为什么不直接用分布式事务？** 跨 Redis 和 MySQL 的 2PC 性能不可接受，秒杀窗口也等不起协调者。我用的是 Saga 的思路：预占是一步，落账是一步，每步都有对应的补偿动作，靠业务主键保证补偿可重入。

**边界我要说清楚**：这套机制保证的是"已被消费的消息一定会收敛"，不保证"Redis 整体丢数据后能自动恢复"。因为 Redis 一丢，预占记录和消息一起没了，MySQL 侧就没有任何线索。这个场景我明确划到对账和人工恢复的范围内，不假装系统能自愈。

## Q37 异步处理订单时，用户如何知道自己最终是否秒杀成功

**结论：给用户一个"未决态"的查询入口，四态查询，最终态以 MySQL 为准。**

异步架构最容易犯的错，是"接口返回了 202，但用户在落库前什么都查不到"。我的设计是让**预占记录本身成为"处理中"这个状态的载体**。

具体是四态：

| 状态 | 判断依据 | 用户看到 |
| --- | --- | --- |
| `processing` | 预占记录存在且状态是 `reserved`，订单表还没有 | 排队中，请稍候 |
| `success` | 订单表已有记录 | 抢到了，去支付 |
| `failed` | 预占记录状态是 `released` | 没抢到 / 名额已回补 |
| `expired` | 超过阈值时间仍在 `reserved` | 超时，正在为你核实 |

关键在于：**预占记录是在 MQ 之前就存在的事实**，所以它天然能回答"我现在到底在哪个阶段"。订单表只能回答"最终成没成"，回答不了"还在不在处理"。两个数据源合起来，才是完整的状态机。

**接口设计**：秒杀接口返回时同时给 `reservation_id` 和 `order_id`，用户拿 `reservation_id` 查未决态，拿 `order_id` 查最终态。查询接口本身做两件事：先读预占记录，如果是 `reserved` 就直接返回 `processing` 并带上 `next_poll_after`，不要去查订单表（省一次 DB）；只有预占是 `released` 或者已经落库，才回落到订单表。

**为什么要给 `next_poll_after`**：让前端按服务端节奏轮询，而不是固定 1 秒死循环。高并发下这一句话能省掉大量无效 QPS。

**推送怎么做**：默认短轮询，因为实现简单、天然容错；量大时升级成长轮询或者 SSE，服务端把"落库成功"这个事件推给等待中的连接。我不选 WebSocket，因为秒杀是一次性查询，不需要长连接的双向能力，长轮询的运维成本更低。

**兜底**：如果一条预占长时间停在 `reserved`，说明消息可能卡住了（消费积压、补偿失败）。这时候查询接口不应该只返回"处理中"，而要触发一次核实——把这条记录推给补偿任务，主动确认它到底该成功还是该回补。**用户不应该为一个已经死掉的消息无限等待。**

## Q38 如果要求成功时立即给用户明确结果，并且付款成功就代表买到了，应该怎么调整

**结论：把"下单落库"从异步搬回同步，Kafka 降级为下游通知；库存在下单时就锁死，支付只做状态迁移。**

这个需求其实在要两件事，要分开答。

**第一件：成功即明确结果。**
我的调整是把 MySQL 事务从消费者搬回网关的请求线程里：Redis 预占成功 → 同步执行落库事务（写订单 + 扣活动库存 + 扣持久库存 + 记幂等）→ **事务提交才返回成功**。事务失败就当场补偿、当场返回失败。用户拿到的就是终态，没有中间态。

原来的 Kafka 链路不下线，但**角色变了**：它不再承担"下单"职责，只负责把"订单已创建"这个事实广播给下游——风控、积分、发券、数据仓库、推荐。这样即使 MQ 挂了，下单主链路完全不受影响。这是我认为最关键的架构解耦点：**交易的正确性不应该依赖消息中间件的可用性。**

**第二件：付款成功即买到。**
这句话的技术含义是：**库存在支付之前就必须被锁定**。所以订单在 `created` 状态时库存已经扣掉了，支付回调只做 `created → paid` 的状态迁移，不参与抢库存。

配套必须有两个机制，否则库存会被未支付订单长期占用：
- **超时未支付自动取消**：定时扫描 `created` 超过 N 分钟的订单，走取消流程回补库存。这个 N 要按业务定，通常 10-15 分钟。
- **支付回调幂等**：以支付流水号为幂等键，重复回调只生效一次，避免重复加库存或重复发货。

**性能代价我要主动讲**：同步落库把吞吐压到数据库事务能力，量级是几千 TPS。但这不等于秒杀就慢了，因为**漏斗的作用就是把到达数据库的请求压缩到库存量级**——1000 件商品最多 1000 个事务，不是 10 万个。真正需要扛 10 万 QPS 的是 Redis 预占那一层，而那一层本来就是同步且极快的。所以"同步结果"和"高并发"不矛盾，前提是漏斗足够狠、库存足够小、限流足够准。

**两种模式的取舍我会明确说**：大促场景我用异步，因为要削峰、要保护数据库，用户可以接受几秒的等待；稀缺高价值商品我用同步，因为用户对"到底抢没抢到"极其敏感，且库存小、并发落库压力可控。**这个选择应该做成活动级配置，而不是全站一刀切。**

## Q39 如果希望通过数据库事务保证结果明确、数据一致，同时允许提前拦截超额请求，怎么设计

**结论：Redis 只做"准入控制"，不做"结果裁决"；MySQL 用条件更新 + 唯一约束一次定案。**

这是我这套设计的核心分层，我会讲得细一点。

**第一层，Redis 阶段的定位必须说清楚：它发放的是"入场资格"，不是"成功"**。Lua 扣减成功，含义是"你排进了前 N 名"，不代表你最终买到了。超额请求在这里被挡掉，根本不碰数据库。这个定位很重要，因为一旦把 Redis 的成功当成业务成功，后面所有的补偿逻辑都讲不通了。

**第二层，MySQL 是唯一裁决者，而且只用一条语句裁决**：

```sql
UPDATE seckill_activities
SET stock = stock - 1
WHERE id = ? AND product_id = ? AND stock > 0
```

看 `affected rows`。等于 1 就是裁决通过，等于 0 就是没货。**不需要先 SELECT 再判断**——那样会多一次查询，还会引入"查的时候有货、扣的时候没货"的竞态。条件更新把"判断"和"修改"合并成一次原子操作，由 InnoDB 的行锁保证。再叠加订单表的 `UNIQUE(activity_id, user_id)`，一人一单也由数据库保证。

**第三层，单向容错原则，这是整个设计的安全底线**：

> **允许 Redis 多放行，绝不允许 Redis 少放行。**

意思是：Redis 库存 ≥ MySQL 库存是安全方向，多放的人会在落库时被条件更新挡掉、然后补偿；反过来 Redis 库存 < MySQL 库存，就意味着有库存永远卖不出去，是少卖。所以我会让 Redis 的初始值取"活动库存和商品可用库存的较小值"，宁可保守。

**第四层，失败即回补**：裁决失败 → 幂等回补 Redis → 返回明确失败。用户拿到的是"没抢到"，不是"不知道"。

**为什么不用分布式锁？** 我做过对比：热点商品上，所有请求抢同一把锁，锁本身就是串行点，QPS 上不去；而条件更新是让数据库用自己的行锁做串行化，粒度更细、没有额外网络往返。锁的价值在多资源协调，不在单行扣减。

**边界**：这套设计保证"不超卖"，但 Redis 和 MySQL 之间仍有短暂偏差窗口。我用对账把这个偏差收敛，而不是声称实时强一致。

## Q40 秒杀有没有参与资格限制？是否所有用户都能参与

**结论：资格是独立的一层，放在限流之后、预占之前，用 Redis 集合做 O(1) 判定。**

我的设计里，参与资格不是"顺便校验一下"，而是漏斗里独立的一层，因为它解决的是**完全不同的问题**：限流解决"你来得太频繁"，资格解决"你根本不该来"。

**资格来源**：预约名单、会员等级、白名单、内部员工、定向券用户。这些数据落在 MySQL 的资格表里，以 `(activity_id, user_id)` 为唯一键。活动开始前统一预热到 Redis 的一个集合里。

**校验位置很关键**：必须在**扣库存之前**。因为没资格的用户如果先占了库存再被拒，就要走一遍补偿，既浪费 Redis 写入，又会在那几十毫秒里让真正有资格的人看到"售罄"。这是"误杀"，比"多放"更难接受。

**数据结构**：只需要判断"在不在名单里"，用 Set 或者 Bitmap。规模大的活动我用 Bitmap，20 万人的资格名单只占 25KB。

**一个设计细节**：资格校验是**只读判断**，可以先查后扣，不需要和扣减严格原子；但"一人一单"是**写判断**，必须和扣减在同一个 Lua 里，因为中间有竞态。这两个校验看起来相似，但对原子性的要求完全不同，我会分开处理。

**第四道防线是风控**，在网关最前面：设备指纹、IP 聚集度、行为频次、黑名单。风控和资格的区别是：资格是"业务规则"，风控是"安全规则"，前者决定你有没有权利参加，后者决定你是不是真人。

**分层的好处**我会总结成一句：**每一层都用最便宜的手段挡住它最擅长挡的那类流量**。风控挡机器，限流挡洪峰，资格挡无关用户，Lua 挡超额请求，MySQL 只处理真正通过所有关卡的那几千个请求。

## Q41 Redis 的 Lua 脚本具体检查哪些内容

**结论：五组校验，而且顺序是设计过的——所有校验都在第一次写入之前完成。**

我把脚本的检查拆成五组，按执行顺序讲：

**第一组，入参合法性。** 用户 ID、活动 ID、商品 ID、订单 ID 必须是正整数，`reservation_id`、`event_id`、金额不能为空。这一组的意义不是防攻击，是**防止脏数据进入事实链**——一旦脏 ID 写进了预占记录和消息，后面每一层都要处理它，代价远大于在这里返回一个错误码。

**第二组，Key 类型校验。** 库存 key 必须是 string，预占记录必须是 hash 或不存在，Stream 必须是 stream 或不存在。为什么要单独校验类型？因为 Redis 对错误类型执行命令会抛运行期异常，而这个异常发生在脚本中途，**已经执行的命令不会回滚**。所以类型必须在动手之前全部确认。

**第三组，幂等分支。** 读预占记录的当前状态，分三种：
- 已经是 `reserved`：逐字段比对业务身份，全部一致就**直接返回成功，不重复扣库存**。这保证消息重投、用户重复点击都是安全的。
- 已经是 `released`：说明这个名额已经被回补了，拒绝，返回"已释放"。
- 是 `prepared`：说明上一次执行到一半进程挂了，允许继续走完，这是崩溃恢复的入口。

**第四组，库存判断。** 库存值必须能解析成数字，且大于 0。小于等于 0 返回售罄。**这里不做任何"预扣留余量"之类的技巧**，因为余量逻辑会让账变得不可解释。

**第五组，用户去重。** 判断这个用户在本次活动里是否已经买过，买过就直接返回，不消耗库存。

**然后是写入顺序，这是我最想讲的设计细节**：

```
写预占记录(prepared) → XADD 消息 → 标记预占(reserved) → DECR 库存
```

为什么是这个顺序？因为 Redis 的 Lua 保证"不被其他命令插入"，但**不保证"出错回滚"**。如果先 `DECR` 再写预占记录，一旦中途失败，就会留下"库存扣了但没有预占元数据"的状态——这个状态无法自动恢复，是真正的丢单。按我这个顺序，最坏情况只会留下一条可检测的 `prepared` 孤立记录，或者一条多余的消息；这两种都能被扫描出来并清理。

**原则一句话**：**宁可留下可检测的垃圾，不可留下不可恢复的隐性成功。**

**最后说清楚脚本不做什么**：不读活动配置、不校验时间窗、不校验资格。因为这些都是只读判断，放在网关层做，用本地缓存扛住；让 Lua 承担配置读取会把脚本变重，而脚本是热点路径上最不能变重的东西。

## Q42 如何记录用户已经购买过？使用什么数据结构

**结论：Redis 做快速判重，MySQL 唯一约束做最终防线，两层各司其职。**

我的设计是**双写，但职责不同**。

**Redis 层，目的是"性能和体验"**。活动维度的购买集合，Lua 里 `SISMEMBER` 判断、`SADD` 标记，和 `DECR` 在同一个脚本里完成。这样重复请求在 Redis 层就被挡住，**连库存都不消耗**。

这一点很重要，我要展开说：如果只在 MySQL 层做唯一约束，用户连点 100 次，Redis 会扣 100 次库存，然后落库时失败 99 次、补偿 99 次。这中间有一段窗口，别的用户看到的是"售罄"——**少卖 + 误杀**。而且 99 条无效消息还要走完 MQ、消费者、事务、补偿，纯属浪费。所以去重必须前置。

**MySQL 层，目的是"正确性"**。订单表上加 `UNIQUE(activity_id, user_id)`。Redis 会丢数据、会主从切换丢写、会被人误删，所以 Redis 的判断只能当"优化"，不能当"真相"。真正的防线是数据库约束，它保证即使 Redis 全挂，也不会出现一个人两个订单。

**数据结构怎么选**，我会讲取舍：
- **只需要判断"买没买"** → Set。语义最直白，O(1)，内存可控。
- **还需要知道"买的哪一单"** → Hash，`userID → orderID`。好处是判重和查订单一次搞定，用户点进去直接能看到订单号，少一次 DB 查询。
- **规模极大且 userID 紧凑** → Bitmap，一人一 bit，20 万人 25KB。

我倾向 Hash，因为秒杀场景用户抢完第一件事就是看订单，顺手存下来很划算。

**一个容易被忽略的设计决策**：取消订单后要不要把用户从集合里移除？这不是技术问题，是业务规则。如果规则是"取消后可以重新抢"，那回补时必须同步移除标记，否则用户永远抢不到第二单；如果规则是"一人一单，取消也不许再抢"（防黄牛），那就保留。我会把它做成活动级配置，而不是写死在代码里。

**为什么不用布隆过滤器做主判重**：布隆有假阳性，会把没买过的人误判成买过，造成误杀。它可以放在最前面做"快速排除"，但后面必须有精确结构兜底。**误杀在秒杀里是不可接受的**，因为用户会投诉。

## Q43 十几万、二十万用户都在一个 Set 里形成大 Key，怎么处理

**结论：先量化，再换结构，最后管生命周期。这不是内存问题，是单分片热点和阻塞操作的问题。**

先给数字，别空谈。Set 在元素超过 512 个之后会从 intset 转成哈希表，每个成员算上 dictEntry、SDS 和负载因子，大约 60-100 字节。20 万成员就是 **15-25MB**，外加约 4MB 的桶数组。

**危害不是内存**，20MB 对 Redis 不算什么。真正的三个问题：
1. **集群下只能落一个 slot、一个节点**。所有判重请求打到一个分片，其它节点闲着。
2. **阻塞式操作**。`SMEMBERS`、`DEL`、`RDB fork`、集群迁移都要遍历或复制这个 key，20 万元素会造成明显的延迟毛刺。
3. **扩容和主从同步都会被它拖慢**。

业界的经验阈值是"集合元素超过 5000 就算大 key"，20 万已经远超。

**方案我按优先级讲：**

**第一选择，Bitmap。** 20 万人只需要 20 万 bit，也就是 **25KB**，比 Set 小三个数量级。同时 `SETBIT`/`GETBIT` 是 O(1)，不会阻塞。唯一的前提是 userID 能映射成紧凑的下标：如果 userID 是全局自增且范围可控，直接用；如果稀疏，就在活动维度做一次"活动内序号"映射，或者按 `userID / 65536` 拆成多个 Bitmap。

**第二选择，分片 Set。** 用 `userID % 32` 拆成 32 个 key，每个几千人。这里有个细节值得讲：**每个分片用独立的 hash tag，才能真正落到不同 slot**。如果用活动 ID 做统一 hash tag，所有分片会挤在同一个 slot，等于白拆。之所以能这么拆，是因为"判断某人买没买"只需要查他自己那一片，**是单 key 操作，不涉及跨 slot**，天然规避了 CROSSSLOT 问题。

**第三，布隆过滤器做前置。** 内存极小，但接受假阳性，只当"快速排除"，后面还得有精确结构。

**第四，治本：管生命周期。** 秒杀的购买集合是**临时热点数据**，不是长期存储。活动结束、对账完成之后，明细归档到 MySQL，Redis 的 key 直接删掉或者设 7 天 TTL。很多"大 key 问题"的本质是"忘了删"。

**我会总结成一句**：大 key 的治理顺序是"换更省的结构 → 拆开 → 加前置 → 该删就删"，而不是"加内存"。

## Q44 Redis 中的库存从哪里来？定期从数据库同步还是独立维护

**结论：一次性预热，不是定期同步。用 SET NX 保证幂等，用版本号防止配置漂移。**

**来源**：活动开始前，从 MySQL 读活动库存和商品可用库存，**取两者的较小值**写进 Redis。取小的原因很实际：活动配置可能写 1000 件，但仓库实际只有 800 件，取小的才不会卖了没货。

**为什么用 `SET NX` 而不是 `SET`**：这是我最在意的细节。预热接口可能被运维重复调用、被重试、被定时任务再跑一遍。如果用 `SET`，第二次调用会把正在销售的库存**重置回初始值**，直接造成超卖。`SET NX` 保证"只有 key 不存在时才写入"，重复调用返回已存在的值，天然幂等。这是线上很容易踩的坑。

**为什么不定期从数据库同步**，三个理由：
1. **数据库在秒杀窗口内是被保护对象**。定期全量同步会给它增加额外压力，和"用 Redis 保护 MySQL"的初衷矛盾。
2. **同步会覆盖正在进行的扣减**。你在 10:00:00 读到 500，10:00:01 写回 500，这 1 秒里卖掉的 20 件就被抹掉了——**脏写**。
3. 秒杀库存的变化是**单向递减**的（除了取消回补），不需要"同步"，只需要"初始值 + 增量事件"。

**那怎么保证不漂移**：用**版本号**。库存 key 里带一个 `epoch`，活动配置变更（比如运营加库存）时 epoch 递增，预热时按 epoch 做 CAS——旧版本的写入会被拒绝。这样"改配置"和"正在销售"就不会打架。再配一个对账任务定期比对两边剩余，偏差超阈值告警。

**一个安全设计**：库存 key 不存在时，我选择**拒绝售卖**，而不是回落到 MySQL 直接查。这叫 fail-closed。因为一旦回落，Redis 故障时所有流量会直接打穿到 MySQL，秒杀瞬间变成"数据库全表扫 + 行锁争抢"，结果一定是雪崩。宁可返回"活动暂不可用"，也不能让故障扩散。

## Q45 秒杀可能几秒钟就结束，定期对账在这里有什么作用

**结论：对账不是为了实时正确，是为了发现"实时机制发现不了的差异"，并把钱和货的账做平。**

这个问题的前提其实是个误解——"秒杀短，所以不用对账"。我会先把这个误解拆掉。

**实时机制能解决什么**：已知的、单点的失败。扣减失败我当场补偿，补偿失败我重投。这些都是"我知道它失败了"。

**实时机制解决不了什么**：**它不知道的失败**。三类典型：

**第一类，两边都少。** Redis 预扣成功，但消息在 Redis 故障中丢了。结果是 Redis 少一个库存、MySQL 少一个订单——**账面完全对得上**，任何实时校验都发现不了。但用户看到的是"我抢到了，订单没了"。只有拿预占明细去比对订单明细，才能发现这个"幽灵缺口"。

**第二类，僵尸预占。** 预占记录停在 `reserved`，但订单永远没落库，活动已经结束了。这条记录占着的名额再也没人释放。实时补偿只在"收到消息"时触发，消息没来就永远不会动。

**第三类，长期补偿失败。** Redis 挂了 10 分钟，这期间所有补偿都失败。虽然消息会重投，但如果活动在故障期间结束、消费者被下线，这批预占就成了无人认领的孤儿。

**所以我的对账设计是两层：**

**第一层，分钟级守护。** 扫"`reserved` 状态 + 超过阈值时间 + 没有对应订单"的预占记录，推给补偿任务去核实：该补单的补单，该回补的回补。这一层有**实时价值**，它把"卡住"变成"推进"。

**第二层，活动结束后的结算对账。** 核两个等式：
- `初始库存 = 已售数量 + 有效取消回补数量`
- `Redis 最终剩余 = 初始库存 - 有效预占数量`

差异落差异表，出告警，进人工处理。这一层是**财务价值**——秒杀涉及真金白银，几十块的差异也必须能解释清楚。

**一条设计原则我会强调**：**对账只读，不直接改库存。** 发现差异之后，回补动作仍然走那个幂等的 release 任务，而不是让对账脚本直接 `INCRBY`。因为对账脚本如果有写权限，它自己出 bug 就会变成二次事故源。

## Q46 Redis 库存和 MySQL 库存分别在什么时候扣减

**结论：Redis 先扣（占位），MySQL 后扣（记账），取消时反向且不对称。**

**Redis 的扣减时机**：网关的同步请求路径上，Lua 脚本内完成。它在写预占记录、发消息之后执行。这个扣减的语义是"**占位**"——这个名字额被这个人占住了，别人不能再拿。

**MySQL 的扣减时机**：消费者的事务里，和"插入订单"在同一个事务。这个扣减的语义是"**记账**"——这批货真的出库了。

**两者的时间差**是几十毫秒到几秒，取决于 MQ 积压。在这个窗口里，Redis 剩余 < MySQL 可售。**这个方向是安全的**，因为它只会导致"少卖"，不会导致"超卖"。我把这个不变量当成设计的安全边界：

> 任何时刻，Redis 剩余库存 ≤ MySQL 可售库存，是允许的；反过来就是事故。

**取消的时候是反向的，而且不对称**，这点值得单独讲：

- **Redis 一定回补**。因为预占确实发生过了，占用确实存在过，必须还回去。
- **MySQL 不一定回补**。要看这个订单**到底有没有真的扣过 MySQL 库存**。因为"提前取消"的场景——用户下单后、消费者还没落库就取消了——这个订单从来没扣过 MySQL 库存，如果取消时盲目加回去，MySQL 库存就会**虚增**，直接导致超卖。

所以我给订单的生命周期记录加了一个状态位，标记"持久库存是否已实际扣减"。取消回补时先看这个位：扣过才加回，没扣过只清 Redis。**这个不对称是设计出来的，不是疏漏。**

## Q47 MySQL 扣减失败后，Redis 库存是立即回滚，还是等待对账补偿

**结论：立即回滚。等对账在秒杀场景下等于主动少卖。**

**为什么不能等**：秒杀的销售窗口是秒级。如果等对账（通常是分钟到小时级），这个名额在整个活动期间都是死名额。假设 1000 件商品有 5 个这样的名额，就是 0.5% 的少卖——而且这 5 个用户还会来投诉。**在秒杀里，时间就是库存。**

**为什么敢立即回滚**：因为回补是**幂等**的。我用 `reservation_id` 加状态机，加上一个稳定的 `release_id` 做二次幂等，保证同一个预占无论被回补多少次，库存只加一次。如果没有这层幂等，立即回滚确实危险——重投会重复加库存，直接超卖。所以**"立即回滚"和"幂等"是一对，必须一起设计**。

**补偿本身失败了怎么办**，这是三级兜底：
1. 立即重试（带退避），大部分 Redis 抖动这一层就解决了。
2. 仍失败 → **不提交 offset**，让消息重投，消费者重新走一遍。因为幂等，重走是安全的。
3. 重投多次仍失败 → 进延迟队列 / 死信，出告警，**最后由对账兜底**。

所以"立即回滚"和"对账"不是二选一，是**快路径和慢路径**的关系：快路径处理 99% 的情况，慢路径接住剩下的 1%。

**什么场景才应该选择"等对账"**：库存充裕、活动周期长（比如持续几天的预售）、或者回补动作会和下一轮预占产生竞争。这类场景下"先记账、后回补"更稳，因为不急着把名额放出去。但秒杀不属于这类——秒杀必须立刻把名额还给下一个人。

## 收尾：如果面试官问"这套设计有什么不足"

不要否认，也不要罗列一堆。挑一个真实的、有思考的边界说：

> 我这套设计明确不做的一件事，是**跨 Redis、Kafka、MySQL 的 Exactly Once**。我做的是"至少一次投递 + 全链路幂等 + 补偿 + 对账收敛"。因为强一致需要分布式事务，性能上不可接受；而秒杀场景真正不能接受的是**超卖**，不是"极少数情况下少卖"。
>
> 所以我的优先级很明确：**正确性上，宁可少卖不可超卖；体验上，宁可让用户多等两秒，不可让他看到一个错的结果。** 这两条决定了我在每个岔路口的选择。

## 附：三个高频追问的应对

**"你说 Redis 扛 10 万 QPS，但每个请求不是还要查一次数据库校验活动吗？"**
> 活动配置是**读多写极少**的数据，我会在网关做本地缓存（启动加载 + 变更事件推送刷新），请求路径上一次 DB 都不查。DB 只在"活动创建/变更"和"落库存"这两个低频、必要的时刻被访问。这是分层缓存的基本要求——热点路径上不能有任何同步的 DB 依赖。

**"Redis 挂了怎么办？"**
> 分两种。读路径：库存 key 不存在就**拒绝售卖**（fail-closed），不回落数据库，避免流量打穿。写路径：预占失败直接返回"系统繁忙"，让用户重试，不产生任何半成品状态。整体原则是**故障时保守，不制造不可恢复的中间态**。

**"如果消息重复消费，会不会重复扣库存？"**
> 三道幂等：`processed_events` 表用事件 ID 判重；预占记录的状态机保证库存只还一次；订单表的唯一约束保证不会有两个订单。三者覆盖了"消息重复"、"补偿重复"、"用户重复下单"三种不同的重复，不是一道防线包打天下。

## 附录 A：状态机怎么讲

**先用一句话给定义，别用术语开场**：状态机不是理论课上的自动机，而是"用有限的状态 + 明确的迁移规则，来裁决一件事此刻能不能做"。没有它，判断"这单能不能取消"就是一堆 `status != paid && !closed && refund == 0`，每加一个业务分支就多一个 if，最后没人敢改；有了它，决策退化成"当前状态在不在允许列表里"。

**四台机的分工（一个状态字段只回答一个问题）**

| 机器 | 权威存储 | 状态 | 回答什么问题 |
| --- | --- | --- | --- |
| 预占状态机 | Redis reservation Hash | `prepared → reserved → released` | 名额有没有被占住 |
| 订单生命周期 | MySQL order_lifecycle.status | `created → succeeded / cancelling → cancelled / rejected` | 这单最终成没成 |
| 库存记账位 | MySQL persistent_inventory_state | `not_applied → applied → restored` | MySQL 库存到底扣没扣过 |
| 释放任务 | MySQL inventory_release_tasks.status | `pending → processing → completed`（失败回 pending） | 回补推进到哪了 |

**为什么要四台而不是一台**：权威存储不同（Redis 会丢数据，MySQL 不会）、时间尺度不同（毫秒 vs 秒）、语义不同（`rejected` 是系统裁决要告警，`cancelled` 是用户放弃不用告警）。硬合并会导致状态爆炸，比如出现 `created_applied`、`created_not_applied`。

**三个必须讲清的设计点**

1. **`prepared` 的唯一目的是让"脚本执行到一半崩溃"可被检测**，它不是业务状态。这是"可检测垃圾优先于不可恢复隐性成功"的落地。
2. **重放不是迁移**：读到已是 `reserved` 且业务字段全等，直接返回成功、不产生任何迁移。迁移可能有副作用，重放必须无副作用。
3. **状态机的死穴不是迁错，是永远停在中间态**。所以每个中间态都要有超时兜底：预占要有超时扫描，`cancelling` 要能被推进，`processing` 靠 `lease_until` 到期被重新领取。租约的本质，是把"进程还活着吗"这个外部事实编码进状态。

**状态机能带来什么（一句话版本）**

> 幂等（已是目标状态即 no-op）、仲裁（条件更新的 affected rows 就是胜负）、可恢复（状态在存储上，不在内存变量里）、可观测（状态是监控和对账的维度）。

**落地三条工程约束**

- 状态值用 `CHECK` 约束枚举，非法值根本写不进去；
- 迁移只允许条件更新 `UPDATE ... WHERE status = 旧值`，禁止"先 SELECT 判断再 UPDATE"；
- 每个中间态必须配超时 + 补偿任务，否则状态机会僵死。

### A.1 "状态机能幂等，为什么还要 reservation_id 做幂等键"

这是必被追问的一问，答案是：**两者正交，缺一不可。**

- **状态机管纵向**：同一条记录在时间轴上被处理多次，第二次读到已是 `reserved`，于是不再迁移。
- **幂等键管横向**：两个不同请求可能代表同一件事，键保证它们落到**同一条记录**上。

状态机只能保证"同一个身份内部"的幂等。若每次请求都生成新 ID，等于每次新建一条记录、新建一台状态机，它永远是初始态 `prepared`、永远允许执行——**跨身份的重复，状态机看不见**。

而且键是状态机的前置条件：预占记录是 `seckill:reservation:{activityID}:{reservationID}`，没有 ID 连 `HGET` 都发不出；回补时 `release_id = "release:" + reservationID`，没有它无法判断"是不是上次那次"。

**四种"同一"，四把键**

| 重复来源 | 要回答的问题 | 幂等键 | 防线 |
| --- | --- | --- | --- |
| MQ 重投 | 这条消息处理过吗 | `event_id` | `processed_events` + offset 不提交 |
| 补偿/取消重复触发 | 这次预占的库存还过了吗 | `reservation_id` | Redis 状态机 |
| 用户连点 | 这个人买过吗 | `(activity_id, user_id)` | MySQL 唯一约束 |
| 客户端超时重试 | 这次下单请求重复了吗 | 客户端 token | 网关前置判重 |

**反例（最有说服力）**：不用 `reservation_id`、只靠"查订单表看买没买过"。用户连点两次，两次都查到"没有订单"（订单还在异步落库），于是都放行、扣两次库存。状态机每一步都严格幂等，系统仍然错了——因为它把"重复"识别错了对象。**幂等的对象错了，幂等本身就没有价值。**

**诚实的边界**：`reservation_id` 由服务端生成，收敛的是消息级与补偿级重复，收敛不了客户端重试（重试会产生新 ID）。要覆盖这一层需要客户端 `request_token`  + 网关前置判重。所以幂等是分层的，不指望一个 ID 解决所有问题。

**一句话版本**

> 状态机是记账规则，`reservation_id` 是凭证号。规则可以说"同一张凭证不能入账两次"，但没有凭证号，你连那张凭证都找不到。

### A.2 唯一标识、幂等表、状态机、乐观锁是什么关系

常见误区：把这四个当成并列的四种"幂等手段"。实际是**一个身份 + 三类守卫**，而且第 3、4 项在实现上是同一行 SQL。

| 名词 | 它其实是什么 | 回答的问题 | 项目对应 |
| --- | --- | --- | --- |
| 唯一标识 | **前提**，不是手段 | 谁是同一件事 | `reservation_id`、`event_id` |
| 幂等表 | 唯一约束的一种落地形态（记录"做过"） | 这件事的结果记录过了吗 | `processed_events` |
| 状态机 | 业务规则：允许哪些迁移 | 现在还能不能做 | `prepared/reserved/released` |
| 乐观锁 | 并发原语：保证判断与修改原子 | 中间有没有人插队 | `WHERE status = 旧值` |

**关键一击：状态机的条件更新本身就是乐观锁。** `UPDATE ... WHERE status = 'created'` 里，`status` 就是 version。所以"状态机"是规则，"乐观锁"是执行规则的手段，两者不是并列关系，是同一行 SQL 的两个视角。

**三类守卫**（这才是真正的分类）

1. **存在性守卫**：结果记录只能有一份 —— 唯一约束 / 幂等表 / `UNIQUE(reservation_id)`。
2. **状态守卫**：过程只能往前走 —— 状态机 + 条件更新。
3. **并发守卫**：同一时刻只有一个推进者 —— 乐观锁 CAS / 租约。

**五道闸门与"去掉会怎样"**

| 闸门 | 机制 | 去掉后的具体故障 |
| --- | --- | --- |
| 请求入口 | 客户端 token | 超时重试产生两个预占，库存被占两次，少卖 |
| Redis 预占 | `reservation_id` + 状态机 | 无法判断是否处理过，重复补偿 → 多加库存 → 超卖 |
| 消息消费 | `event_id` + 幂等表 | 同一条消息重投产生两笔订单 |
| MySQL 落库 | 唯一约束 + 条件更新 | 用户连点成多单、并发扣减超卖 |
| 回补任务 | `release_id` + 租约 | 重复取消触发多次回补，库存虚增 |

每道闸门去掉后坏的方式都不一样 —— 这是"不是冗余"的证明。

**判断是否过度设计的三问**

1. 这层防的失败模式，别层在**同一时间窗**防得住吗？（时间窗重叠 = 冗余）
2. 这层的成本远低于它避免的损失吗？（Redis O(1) vs 少卖）
3. 去掉它，是否能观测到一个具体的故障？（说不出 = 堆砌）

**一个精确的差别（可能被追问）**：幂等表如果只存 `event_id`，它是**去重表**，只能拒绝重复；如果还存 `response`，它是**真幂等表**，重试时可以直接返回上次结果。`processed_events` 属于前者；要做"重试直接返回上次订单号"，需要补一列结果。

## 附录 B：两分钟完整口述稿

面试官说"你讲讲秒杀链路"，照这段说。六段，每段先讲做什么，再讲为什么这么设计。

**第一段，接入。**
请求进网关先过三关：参数与身份校验、限流、活动有效性。限流是分层的——本地令牌桶挡单机突发，Redis 三级配额挡全局、单商品、单用户超量；活动配置走本地缓存，不在热点路径查库。这一段的目的不是业务，是把不该进来的流量挡在 Redis 之前。限流必须在最外层，因为 Redis 连接池是最不能被刷满的资源。

**第二段，预占。**
一次 Lua 脚本里做五件事：判断库存、判断这个用户在本活动是否已经买过、写预占记录（状态 prepared）、投一条消息进 Stream、状态改 reserved，最后 `DECR`。
这里要强调：**Redis 的库存是真的减了，不是只打标记**。减的是"可售名额"，MySQL 还没动，这个差值就是在途订单。
脚本的顺序是刻意的：所有校验在第一次写入之前完成，因为 Redis 的 Lua 运行时出错不会回滚已执行的命令；写入顺序是 `prepared → XADD → reserved → DECR`，最坏只会留下可检测的孤立记录，绝不会留下"扣了库存却没有预占元数据"这种不可恢复的状态。
预占成功返回 202，带 `order_id` 和 `reservation_id`。

**第三段，可靠投递。**
Redis 到 Kafka 之间不是直连，中间有 Stream 做 outbox。Publisher 以消费者组读 Stream，投给 Kafka，**只有 Kafka ack 之后才 XACK**。所以 Kafka 短时不可用不会丢消息，恢复后继续投；进程崩溃留下的 pending 消息会被重新认领。这一跳的意义是：Redis 预占成功这件事，必须能可靠地传到下游。

**第四段，落库。**
Consumer 在一个 MySQL 事务里做四件事：幂等表判重、订单生命周期仲裁、插订单、条件更新扣活动库存和持久库存，最后写已处理事件、提交 offset。
关键是用**条件更新**而不是先查后改：`UPDATE ... WHERE stock > 0`，看 affected rows，等于 1 才算裁决通过。这样"判断"和"修改"是一次原子操作，不会被并发插队。订单表上还有 `UNIQUE(activity_id, user_id)` 做一人一单的最后防线。

**第五段，结果。**
用户拿 `order_id` 轮询：命中预占记录且状态是 `reserved`，就是处理中；命中订单表，就是成功；预占状态是 `released`，就是失败已回补。所以"处理中"这个状态是由预占记录承载的，不是靠猜。

**第六段，回补。**
取消要分两种，这是最容易设计错的地方。落库**前**取消，MySQL 从来没扣过，只回补 Redis；落库**后**取消，两边都扣过，两边都要回补。判断依据是一个独立的状态位，记录"持久库存是否已实际扣减"，不能靠订单状态推断——因为盲目回补 MySQL 会让库存虚增，直接造成超卖。
回补本身是异步的：先落取消意图和一条持久化的回补任务，Worker 领取执行，接口返回 pending。因为跨 Redis 和 MySQL 两个系统，不可能在一个事务里完成。回补用稳定的 `release_id` 做幂等，任务带租约，进程挂了任务能被其他实例接管。
另外"抢到但没付款"也要走同一条回补流程，靠超时关单触发，否则库存会被未支付订单锁死。

**收尾一句**：整条链路的一致性策略是"至少一次投递 + 全链路幂等 + 补偿 + 对账收敛"，我不宣称跨 Redis、Kafka、MySQL 的 Exactly Once。因为秒杀真正不能接受的是超卖，不是极少数情况下的少卖。
